# 任务1.1：微信开发者工具交互冒烟测试与问题修复 方案

## 一、任务定位

任务1 已交付 MVP，本任务不新增大功能，重点是：**真实运行验证 + 交互链路确认 + 发现问题最小修复**。

## 二、环境限制说明（关键）

**本机无微信开发者工具 GUI，无法做真机/模拟器预览验证。** 这意味着任务文档第 2、3、4、5、6 节中的「微信开发者工具导入测试」「触摸操作」等无法由 AI 直接执行。

**替代验证方案**：构建一个 **Node 下的微信运行时模拟器**，把 wx 全局、canvas、touch 事件、requestAnimationFrame、storage 全部 mock 掉，让 `main.ts` 的真实 bootstrap 流程跑起来，并通过注入 touch 事件驱动一整局。这比静态审查强得多，能覆盖：
- 入口加载链路（game.js → dist/main.js → bootstrap）
- 微信 API 调用兼容性（getSystemInfoSync / setStorageSync / onTouchStart 等）
- Canvas 绘制调用完整性（不抛错、调用次数合理）
- requestAnimationFrame 主循环驱动
- 触摸 → 移动 → 战斗 → 结算 → 升级 → 存档 全链路

但**无法覆盖**：真实渲染像素、触摸硬件手感、微信开发者工具特定行为。这些需用户手动补验，成果说明中明确列出。

## 三、微信运行时风险点（已通过代码审查识别）

| # | 风险 | 位置 | 修复策略 |
|---|---|---|---|
| 1 | 全局 `requestAnimationFrame` 在 wx 可能未定义 | GameManager.start | 优先用 `canvas.requestAnimationFrame`（wx canvas 有），回退全局 |
| 2 | 触摸 `clientX/clientY` 在 wx 是物理像素，需与逻辑坐标系一致 | Input | 微信 touch 的 clientX 已是逻辑像素（windowWidth 基准），与 canvas scale 后一致；但需确认 |
| 3 | 敌人首次接触玩家时 attackTimer 可能已累积超 interval，瞬间触发一次伤害（非 bug 但手感差） | EnemyMouse | 接触开始时把 attackTimer 归零，首个间隔从接触瞬间算起 |
| 4 | touchStart 同时设 tap + 摇杆起点，移动后再点按钮会误判 | Input | 区分：tap 仅在短按+小位移时触发；长按拖动不触发 tap |
| 5 | BattleManager 没有结算后停止 update 的强保护（ended 标志有，但 render 仍可能访问空 player） | BattleManager | ended 后 render 早退 |
| 6 | ResultUI / MainUI 在 game.lastOutcome=null 时可能空指针 | ResultUI | 已有判空，再确认 |

## 四、允许的增强（小范围）

- Debug 开关：`wx.getStorageSync('debug')==='1'` 时输出关键日志
- 一键重置存档入口（仅 debug）
- 按钮命中范围 padding（触摸更宽容）
- 触摸移动死区/手感微调

## 五、验证闭环

1. 修复前：先写微信运行时模拟器 + 集成冒烟测试，**让它先暴露问题**
2. 修复：针对暴露的真实问题做最小修复
3. 修复后：测试转绿 + 原有 25 测试不退化
4. 全量验证：typecheck + build + test 全绿
